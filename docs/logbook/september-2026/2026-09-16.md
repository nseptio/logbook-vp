## 1. Monitoring & Prosedur Restart Daemon Feed ITCH JATS di Server

Untuk menyuplai data antrean pasar secara terkini, server Linux menjalankan beberapa service latar belakang (*daemon*) yang terhubung langsung ke aliran data bursa efek (JATS ITCH):

- **`CitHrf.service`** (*ITCH Receiver Feed*): Bertugas menerima paket aliran data mentah dari jaringan bursa.
- **`CitHdf.service`** (*ITCH Data / Dispatcher Feed*): Bertugas memproses dan mendistribusikan data transaksi ke memori internal sistem.

### Pemantauan Berkas Log Transaksi

Aktivitas penangkapan data bursa dapat dipantau secara langsung melalui beberapa berkas log dan data kontrol:

![Monitoring Feed ITCH dan Kontrol Sequence](/images/september-2026/2026-09-16/01.png)

Berdasarkan tampilan terminal pemantauan di atas:

1. **`I2DfAll.df` (Panel Kiri):**  
   Menampung rekaman data *feed* mentah transaksi bursa IDX secara langsung. Setiap baris mencatat detail perdagangan saham (seperti `TKIM`, `PTBA`, `TLKM`, `UNTR`) mencakup waktu transaksi, nomor sekuens bursa, papan perdagangan (`NG` / `RG`), harga transaksi, serta kuantitas volume order.
2. **`recvfeed.log` (Panel Kanan Atas):**  
   Mencatat log pemrosesan paket data yang masuk dari daemon penerima. Berkas ini juga memantau stabilitas aliran data, seperti nomor paket yang sedang diproses (`No packet = [10]...`) serta peringatan kapasitas antrean pesan sistem (*Message queue full*).
3. **`datafeed.date` (Panel Kanan Bawah):**  
   Berkas kontrol urutan data feed yang berlokasi di `/home/HTS_V1/dat/datafeed.date`. Berkas ini menyimpan informasi tanggal perdagangan aktif (`DATE=20260916`) dan nomor sekuens terakhir yang telah diproses (`SEQ=07977111`).

### Prosedur Restart Daemon Order Book Feed

Apabila terjadi desinkronisasi data atau antrean perlu ditarik ulang dari awal sesi perdagangan harian, dilakukan prosedur restart dengan tahapan berikut:

1. **Menghentikan Service:**  
   Menghentikan service penangkap data feed bursa menggunakan alias user systemd:
   ```bash
   sysoff CitHrf.service
   sysoff CitHdf.service
   ```
   *(Keterangan: alias `sysoff` menjalankan perintah `systemctl --user stop`).*

2. **Mereset Nomor Urut Sekuens:**  
   Membuka dan mengedit berkas kontrol `/home/HTS_V1/dat/datafeed.date`, lalu mengubah nilai `SEQ` menjadi `0`:
   ```text
   DATE=20260916
   SEQ=0
   ```
   Langkah ini bertujuan agar daemon membaca kembali rekaman paket transaksi bursa dari nomor sekuens pertama pada hari tersebut.

3. **Menjalankan Kembali Service:**  
   Menyalakan kembali kedua daemon secara berurutan:
   ```bash
   syson CitHdf.service
   syson CitHrf.service
   ```
   *(Keterangan: alias `syson` menjalankan perintah `systemctl --user start`).*

## 2. Cara Kerja Streaming `RT_Q10` pada Legacy FormD (Secara Umum)

Pada lingkungan sistem desktop legacy Form Designer (FormD), pembaruan data Order Book 10 tingkat (*Level 2 Market Depth*) tidak berjalan secara polling berulang, melainkan mengandalkan kerja sama antara dua komponen:

### Peran `dscat` vs `rtupdate`

- **`dscat` (`ds100001` - In-Memory Data Store):**  
  Ketika pengguna pertama kali memilih kode saham, `dscat` melakukan permintaan data awal (*snapshot*) melalui transaksi TR 100001. Fungsinya adalah mengisi memori penampung data awal agar tabel antrean pada antarmuka tidak kosong. `dscat` sendiri bersifat statis dan tidak memiliki kemampuan mendengarkan siaran data.
- **`rtupdate` (`rtQ10_100001` - In-Place Delta Mutator):**  
  Komponen ini bertugas mendengarkan aliran siaran data langsung (*real-time feed*) dari bursa untuk saham yang bersangkutan (`RT_Q10`). Ketika bursa mendeteksi adanya order baru, pembatalan order, atau transaksi yang cocok, `rtupdate` langsung memperbarui (*mutate*) nilai-nilai di dalam memori penampung `dscat` secara langsung di RAM tanpa perlu melakukan pemanggilan ulang ke database.

### Struktur Kolom yang Ditampilkan

Data yang diikatkan ke tabel tampilan antrean mencakup:
- **Tingkat Harga & Volume Antrean:**  
  10 tingkat antrean beli (`bid1` s/d `bid10` beserta volume lot `bid1v` s/d `bid10v`) dan 10 tingkat penawaran jual (`off1` s/d `off10` beserta volume lot `off1v` s/d `off10v`).
- **Kolom "Add" (`bid1a` s/d `bid10a` & `off1a` s/d `off10a`):**  
  Kolom ini merepresentasikan **jumlah atau frekuensi antrean order** (*order count / queue frequency*) yang sedang menunggu pada tingkatan harga tersebut, bukan jumlah lot tambahan.

### Respons Tampilan Antarmuka

Setiap kali data baru tiba dari aliran siaran bursa, skrip kontrol form secara otomatis:
1. Membandingkan harga transaksi pasar terakhir terhadap posisi `bid1` dan `off1` untuk memberi warna penanda (*highlighting*) pada sel harga yang sedang aktif ditransaksikan (`setCurPriceQuote`).
2. Menjalankan perintah penggambaran ulang tabel antrean (`ugrid3.Redraw()`) sehingga angka volume dan harga terbaru langsung terlihat oleh pengguna tanpa kedipan (*flicker*) layar.

## 3. Kendala dan Temuan pada Aplikasi Flutter (MyBESTI)

Saat meninjau implementasi fitur Order Book pada aplikasi Flutter klien (`mybesti-mobile-trading`), ditemukan beberapa kendala teknis dan perbedaan arsitektur:

### Mekanisme Streaming Tersedia Namun Tidak Digunakan (Di-Komen)

Struktur kode untuk berlangganan data siaran langsung sebenarnya sudah tersedia di dalam proyek, namun saat ini dalam kondisi **dinonaktifkan / dikomentari**:

1. **Pendaftaran Stream di Halaman Order Book:**  
   Pada berkas `lib/pages/buysell/buysell.dart` (baris 104–107), pemanggilan fungsi langganan aliran data saat halaman dibuka dinonaktifkan:
   ```dart
   // SocketService2().rtQ10Add(
   //     code: OrderProvider.of(
   //   routeObserver.navigator!.context,
   // )?.orderParameter.stock);
   ```
2. **Penerusan Data Siaran ke State Management:**  
   Pada berkas `lib/utils/socket2.dart` (baris 1039–1041), penangan paket data siaran bursa (`QUOTQ` dengan penanda aliran `0x10` untuk `RT_Q10`) sudah memetakan parsing XML, namun pemanggilan pembaruan data ke Cubit dikomentari:
   ```dart
   registerHandler(quotqNO, (result) {
     // print('QUOTQ Type C (0x10) result ${result}');
     // BlocProvider.of<OrderBookCubit>(context)
     //     .setOrderbook(response: result);
   });
   ```
3. **Pemuatan Data Masih Bersifat Sekali Panggil (Snapshot):**  
   Pada berkas `lib/cubit/order_book_cubit/order_book_cubit.dart` (baris 46–61), pemanggilan data Order Book hanya mengandalkan satu kali permintaan TR 100001 (*fire and forget*). Akibatnya, tampilan antrean saham di aplikasi tidak bergerak dinamis mengikuti pergerakan bursa kecuali halaman dimuat ulang.

### Tantangan Arsitektur: Aliran Data Tanpa WebSocket

Komunikasi data pada aplikasi ini tidak menggunakan protokol web modern (seperti WebSocket, Server-Sent Events/SSE, atau gRPC), melainkan menggunakan koneksi soket TCP mentah (*raw TCP socket*) ke port gateway backend (port `51871`).

Hal ini menimbulkan tantangan dalam menelusuri bagaimana server mengelola alur data:
- Aplikasi klien harus mengirimkan paket biner registrasi pendaftaran minat saham (`rtQ10Add`) ke port yang sama dengan pemanggilan TR transaksi biasa.
- Server kemudian secara asinkron menyemprotkan paket siaran bursa bertanda `QUOTQ` melalui koneksi soket yang tetap terbuka tersebut.
- Masih diperlukan penelusuran lebih lanjut mengenai kapasitas dan keandalan gateway server dalam mengelola banyak antrean soket klien secara bersamaan tanpa adanya *handshake* protokol streaming standar.
